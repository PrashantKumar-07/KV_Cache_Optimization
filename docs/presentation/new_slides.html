05 · The key property

KV tokens are immutable — so a stored copy never goes stale

Once prefill writes a token's K and V, they never change again. Three consequences follow — and they're the foundation of the proposed architecture.
Data typeLifecycleConsequence
Model weightsread-only, residentcache normally
Activationswrite, read once, dieshort-lived, no reuse
KV cachewritten once, read many, never modifieda stored copy can never go stale
01

Write-once / read-maybe

A KV token's access pattern is the exact asymmetry profile a non-volatile memory is good at. We pay the expensive direction rarely, the cheap direction often.

02

A copy held anywhere is permanently valid

No coherence protocol, no dirty bits, no invalidation. A backup copy in the cold tier is bit-identical to the live copy forever.

03

'How many times must this token be written?' becomes a design variable

Not a fixed cost. The write-once victim cache (slide 16) re-uses backups instead of re-writing — on real LongBench runs it avoided 91.4 % of decode-time cold-tier writes.

Related work, stated openly: FlexiCache (MLSys 2026) also uses immutability — it offloads each KV page once to a full host-DRAM mirror. TieredKV differs in where writes are the scarce resource: a bounded, write-expensive non-volatile cold tier, where every write is counted and shadows are reclaimed under overflow.

05 · The key property

Why STT-RAM for the cold tier — and why its writes are the problem

STT-RAM (spin-transfer-torque magnetic RAM) stores each bit in the magnetic orientation of a tiny junction. It is a natural home for KV rows that are read often and almost never changed — as long as we avoid writing to it.
Strength

Dense and non-volatile

It doesn't need constant power to hold data, making it inexpensive to keep massive archives online and ready to use.

Strength

Reads are cheap

A read only senses the junction's resistance, so it is fast and low-energy — ideal for rows we merely look at.

Weakness

Writes are slow and costly

Every write must flip the magnetization with a current pulse: more time and more energy per bit than a read, and it wears the cell.

Design rule that follows
Read the cold tier freely; write to it as rarely as possible. Because KV rows never change (previous slide), a row written once can be re-used forever — the write-once victim cache (slide 16).

06 · Proposed solution

TieredKV — a two-tier, write-aware KV hierarchy

Evaluated configuration: hot 992 + cold 2,048 rows per layer, exposure quota 32. In the evaluation both tiers live in GPU memory; STT-RAM latency/energy are modeled from assumed per-bit prices.

06 · Proposed solution

The decode loop — per generated token, per layer

Five stages run after every model call. Each counter — promotions, demotions, paid writes, avoided writes and drops — is recorded per layer per step, so the write saving is counted, not inferred.
01

ATTEND

Unmodified model kernel

Exact attention over the visible set: every hot row, ≤ 32 exposed cold rows and the new token. No approximation inside attention.

→
02

FEEDBACK

Model's own weights

Attention weights update each hot row's cumulative score and age, and record how much each exposed cold row was attended.

→
03

PROMOTE

Cheap direction · read

Up to 32 most-attended cold rows move to the hot tier; a re-entry gate stops ping-pong. The cold copy is kept as a shadow.

→
04

EVICT & DEMOTE

Expensive direction · write

Hot tier over budget → lowest score ÷ age leaves. Shadow exists → reactivate, 0 writes. Otherwise append, 1 write. Cold full → reclaim shadows, then drop LRU rows.

→
05

EXPOSE

Prepare next step

Choose the ≤ 32 most recently used live cold rows that will be visible to attention in the next step.

loop
After stage 05 the next token is generated and the loop restarts at 01. Sinks (4) and the recent window (128) are never eviction candidates; a just-promoted row gets one step of grace.

07 · Proposed mechanism

Write-once victim cache — now measured on a real model

A token is written to the cold tier once. Promotion keeps that copy as a shadow; a later demotion reactivates it instead of writing it again. This cuts write traffic but costs extra memory — both effects are measured below.
↓ Benefit — fewer cold-tier writes
Over all 1,474 LongBench inputs (hot 992), decoding needed 57.5 M demotions; 52.6 M re-used a shadow and only 4.96 M paid a write — 91.4 % avoided. Counting the initial prompt placement as writes too, 40.7 % of all cold-tier writes in a request are avoided.
↑ Cost — more memory
Shadows and the cold tier take capacity. Configured KV payload is 398.5 MB per request for TieredKV (hot 992 + cold 2,048 rows) versus 134.2 MB for a 1,024-row compressed cache — about 3×. When the cold tier fills, shadows are reclaimed first, then the least-recently-used live rows are dropped.

08 · Results — accuracy

Same hot budget: TieredKV stays close to the full cache

FIG. 1
Reading the chart

All compressed methods keep 1,024 rows on the GPU. TieredKV additionally keeps 2,048 cold rows and lets 32 of them join attention.

What we see

6-task average: TieredKV 38.8 vs full cache 41.8. The adapted baselines reach 32.1–33.8. On TriviaQA TieredKV matches the full cache (87.3 vs 87.2).

Caveat

TieredKV holds more total KV (cold tier) than the baselines, so this is equal hot budget, not equal memory.

08 · Results — accuracy

Same attended rows: 992 hot + 32 cold = 1,024

FIG. 2
The stricter setting

Hot tier shrunk to 992 so every method attends to at most 1,024 cached rows per step — verified from the actual tensor sizes in all 10,318 runs.

Result

6-task average 38.5 (vs 38.8 with hot 1,024). Still +4.7 to +6.4 points over the adapted 1,024-row baselines on average; the best compressed method in the chart on all 6 tasks.

Why it helps

Tokens evicted from the hot tier are not lost — the most useful ones come back through exposure and promotion.

08 · Results — what the design costs

The price: about 3× KV storage and slower decoding today

FIG. 4
FIG. 5
Memory

Configured KV payload 398.5 MB (hot 992 + cold 2,048) vs 134.2 MB for the 1,024-row baselines. The cold tier is meant to live in cheaper, denser STT-RAM — but it is still extra capacity.

Measured latency (L40S)

TieredKV ≈ 75–78 ms/token from 1K–16K context, vs 23–34 ms for the others. The policy runs as Python/PyTorch after every layer and needs eager attention for feedback; a fused kernel is future work.

Traffic time (analytical)

Real per-step event counts × assumed bandwidths (STT 50 / 12.5 GB/s read/write, VRAM 864 GB/s). TieredKV is 4–10× below the full cache but 1.7–3.6× above the other compressed methods, because cold rows are read at STT-RAM speed.

Strength
Against baselines with the same fixed GPU budget, TieredKV recovers most of the gap to the full cache: +4.7 to +6.7 points on average.
Honest position
The official SnapKV is 0.7–1.0 points higher on average. It keeps less KV in total (no cold tier), but its cache grows during decoding, so the two use different resources — no state-of-the-art claim is made.
Main contribution
A write-aware hierarchy that keeps quality close to strong eviction methods while avoiding ~91 % of decode writes to the non-volatile tier.

10 · Outlook

Limitations and next steps

Limitations today
  • STT-RAM is modeled, not real hardware: latency and energy use assumed per-bit prices; write counts are logical events.
  • More memory: about 3× the KV payload of a 1,024-row compressed cache.
  • Slower decoding in the current implementation (~75 ms vs 23–34 ms per token).
  • Batch size 1, one model (Mistral-7B), six LongBench tasks.
  • The official SnapKV is slightly more accurate on average.
Next steps
  • Equal-total-memory comparison against official SnapKV, IceCache and RocketKV, charging every buffer.
  • Fused GPU kernel for feedback, promotion and exposure to remove the latency overhead.
  • Run the cold tier on real host DRAM / CXL to measure transfers instead of modelling them.
  • Fresh ablations of the cold-placement fraction and hot/cold split.
  • More models (Llama-3-8B) and longer contexts.
