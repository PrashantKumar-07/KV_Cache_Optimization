## Exception-lifecycle weakness in original diagnostic runner

`current_controller_parity/run_parity.py:60-64` creates `PromptQueryCapture`, then optional `SharedAppendLease`, then model output hook **before** entering per-arm `try/finally`. If lease or output-hook registration fails, earlier objects/hooks are not closed by that finally. PromptQueryCapture itself installs layer hooks incrementally, so a constructor failure could leave a partial hook set. Cleanup (`:77-80`) executes removals/closes/reset sequentially; a close failure can prevent later cleanup. The outer finally preserves report, but does not independently close partially initialized arm resources. Current successful evidence is unaffected: all recorded hook counts match after close. This is an untested exception path, not proof that an exception actually leaked in the completed run.

For future runners, enclose creation in cleanup scope and register each successfully created object with `ExitStack` (or nested finally), preserving original runner/raw hashes. Constructor rollback requires its own invariant if partial registration is possible. Do not mutate this frozen successful runner, and do not infer lifecycle failure recovery from the normal-path hook check. A later isolated CPU mocked failure test can verify the new runner cleanup without GPU expense.
