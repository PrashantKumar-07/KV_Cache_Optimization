## Ranked findings

1. **P2 research-accounting assumption: persistent sketch construction/maintenance is absent from the standalone analytical boundary.** `src/tiered_kv_cache.py:280-326` obtains the entire cold K tensor and computes min/max reductions on every invocation, including unchanged cache inputs. `step():951-953,1021` charges only two H×D vectors per physical cold page. `src/cost_model.py:187-195` says sketches are held in STT but no persistent sketch tensor exists. The CPU probe observes a 32-row, page16, H2,D4 BF16 cache accessing512B cold K to produce64B bounds, yet analytically bills64B. This ratio8 is **not measured traffic or an automatic8× error in total latency**: it quantifies alternative full-reconstruction and ideal persistent-metadata boundaries. Python reductions may legitimately emulate an ideal persistent hardware index, but that assumption is currently implicit and excludes initial construction, updates and index storage. Cold live membership changes at promotion/shadowing (`:605`), shadow restore (`:793,805`), append (`:813`), and compaction (`:610,929`); row compaction can shift every later page boundary. Exact removal of a current min/max needs recomputation or richer metadata, whereas conservatively retaining old extrema preserves the upper-bound property but changes candidate selection. **Minimal remedy:** explicitly name this result an ideal persistent-bound-read model and list excluded construction/maintenance/storage. If simulator results become a contribution, add a separately named full-K reconstruction sensitivity, or implement tested persistent bounds with explicit invalidation/maintenance costs. Do not silently add Python-emulator work to current hardware timing, or apply this finding to LongBench, whose selection has no sketch call.

2. **P2 experimental mixed-precision inconsistency: metadata width inherits cold payload width.** `src/tiered_kv_cache.py:301-304` converts FP8 cold keys to the hot compute dtype before bounds; `:1021` uses `CostModel.sketch_read_cost`, whose element width is STT payload width (`src/cost_model.py:83-84,118-129,187-195`). In the BF16-hot/FP8-cold CPU probe computed bounds occupy64B but are priced as32B. There is no persistent metadata representation that justifies assuming1B bounds. **Minimal remedy:** declare a separate sketch metadata element width, default to actual bound dtype for this emulator/ideal model, and use byte-based explicit metadata billing. Merely quantizing extrema to FP8 can break the bound: min must round outward/down, max outward/up. If no current sketch/FP8 results are claimed, keep this path experimental and forbid its analytical metadata claims until corrected. No effect on current LongBench quality or no-sketch modeled attention fields.

3. **P3 unit-label ambiguity: leakage coefficient is named mW/MB but code divides by2^20.** `src/cost_model.py:37,168-170` implements mW/MiB while `TierSpec` declares MB. Under decimalMB the result is4.6326% lower (ratio1e6/2^20). **Minimal remedy:** label the assumption mW/MiB consistently, preserving numerical values/history, or deliberately convert and version the coefficient/model. Leakage is a separate optional field, so do not relabel dynamic-energy results.

## Verified arithmetic and sensitivity

Primitive traffic dimensions are consistent: one decimalMB at nominal50/12.5GB/s costs20/80us, and assumed2/8pJ/bit costs16000/64000nJ. Promotion/demotion sum source reads and destination writes using per-tier bytes. Bandwidth scenarios yield1MB read/write latencies commercial185.185/185.185us, pessimistic47.619/190.476us, nominal20/80us, optimistic10/40us. Energy remains unchanged because bandwidth changes no energy coefficients; this is correct for that restricted sensitivity, **not evidence that real devices conserve energy across bandwidth changes**. Commercial bandwidth is symmetric while energy assumptions remain asymmetric, explicitly independent assumptions. An energy sensitivity needs its own read/write price scenarios; leakage additionally needs a declared elapsed interval. Analytical byte sums exclude interface/controller/compute/metadata maintenance and concurrency/overlap. They should remain traffic-service budgets, not full-loop latency estimates.

Current `step` fixes correctly capture pre-sketch physical page count and avoid a phantom zero-cold-page read. Counting metadata for all physical pages, including all-shadow pages, is conservative and legitimate under a full metadata-scan assumption; MACs count valid scored pages only. Do not force matching counts without first choosing whether the hypothetical index tracks live pages cheaply. The hot-K median threshold (`:382-397`) performs another real tensor access in the emulator; omission can be an ideal reuse assumption, so it belongs in boundary documentation rather than an unsupported device-traffic assertion.
